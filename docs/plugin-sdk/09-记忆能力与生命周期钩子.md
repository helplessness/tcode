# 记忆能力与生命周期钩子

Plugin SDK `1.3.0` 把记忆作为显式 Host Capability 提供。插件不再导入内部 Memory Manager、猜测存储路径或依赖后台事件是否来得及执行；所有访问都经过 Service 声明、Manifest 权限和 Scope 校验。

## 1. 声明能力与权限

```json
{
  "requires": ["tcode.memory@1", "tcode.events@1"],
  "contributes": ["events"],
  "permissions": [
    {
      "scope": "memory.read",
      "patterns": ["session:*", "team:*"]
    },
    {
      "scope": "memory.write",
      "patterns": ["session:*", "team:research"]
    },
    {
      "scope": "memory.promote",
      "patterns": ["session:*", "team:research"]
    }
  ]
}
```

`requires` 决定 `ctx.memory` 是否存在；`permissions` 决定每次调用能触达哪个目标。权限目标格式固定为：

| Scope | `scope_key` | 权限目标示例 |
| --- | --- | --- |
| `global` | 不允许 | `global` |
| `team` | 必填 | `team:research` |
| `worker` | 必填 | `worker:reviewer` |
| `session` | 必填 | `session:session-123` |

首版只向 `controlled-host` 插件提供直接记忆能力。未知社区插件仍运行在隔离 Worker，不能申请 `memory.*`；后续应通过 Capability Broker 单独开放，而不是暴露存储文件。

## 2. 读写与提升

```python
from tcode_agent.plugin_sdk import PublicEvent


class Plugin:
    async def start(self, ctx, config):
        self.ctx = ctx
        ctx.events.subscribe(
            PublicEvent.SESSION_COMPACTION_BEFORE_V1,
            self._before_compaction,
        )

    async def _before_compaction(self, event):
        session_id = str(event.data["session_id"])
        messages = event.data.get("messages", ())
        if not messages:
            return
        await self.ctx.memory.put(
            scope="session",
            scope_key=session_id,
            content="压缩前已捕获关键上下文",
            tags=("compaction", "plugin"),
            structured={"outcome": "captured"},
            idempotency_key=str(event.data["operation_id"]),
        )
```

公开方法：

- `query(...)`：按文本、层级和过滤条件召回；结果不包含 embedding 或内部检索字段。
- `put(...)`：写入记忆；`idempotency_key` 相同的重试返回已有条目。
- `delete(...)`：删除单条记忆。
- `promote(...)`：复制到另一个 Scope；`move=True` 时还需要源 Scope 的删除权限。
- `cleanup_scope(...)`：清空整个 Scope，需要高权限 `memory.maintenance`。

`promote` 会分别校验源读权限、目标写权限和两端 `memory.promote` 权限，避免插件借提升绕过 Scope 隔离。

## 3. 记忆操作钩子

Host 内部为每次记忆操作生成 `operation_id`：

| 内部 Hook | 语义 |
| --- | --- |
| `memory.recall.before/after` | 召回前变换请求、提交后观察结果摘要 |
| `memory.write.before/after` | 写入前变换或拒绝、提交后观察记忆 ID |
| `memory.delete.before/after` | 单条或整 Scope 删除前后 |
| `memory.promote.before/after` | Scope 提升前后 |
| `memory.operation.error` | 任一操作失败 |

`before` 串行且会等待完成，可修改受限请求字段或把 `action` 设为 `deny`；`after/error` 是并行观察通知，不能改写已提交状态。公开 SDK 只暴露提交后的版本化记忆事件，插件应通过 `ctx.memory` 发起状态修改。

## 4. 压缩时序

一次普通或紧急压缩按以下边界投递：

1. `SESSION_COMPACTION_BEFORE_V1`：串行等待，提供有界消息快照；插件可在回调中完成记忆召回、写入或提升。
2. Host 刷新 Learning Reflection，并生成模型摘要或确定性回退摘要。
3. Host 替换 Session 消息。
4. `SESSION_COMPACTION_AFTER_V1`：提供摘要、token 统计和是否使用回退。
5. 应用阶段异常时投递 `SESSION_COMPACTION_ERROR_V1`。

消息快照最多 32 条、正文总量最多约 32,000 字符；它是生命周期输入，不是无限制导出 Session 的通道。

## 5. 会话删除时序与保留规则

会话删除按以下顺序执行：

1. 等待 `SESSION_DELETE_BEFORE_V1`，让插件完成必要的导出或提升。
2. 为兼容旧插件投递一次内部 `session.delete`；新插件不要订阅它。
3. 删除 `session:<session_id>` 记忆；若该 Session 是 Manager，同时删除同 ID 的 Team 记忆。
4. 删除该 Session 的 Learning Reflection，但保留跨 Session 复用的 Worker Reflection。
5. 写入耐久 `session.deleted` Tombstone，并删除 SQLite 查询投影。
6. 投递 `SESSION_DELETE_AFTER_V1`，其中包含实际记忆清理报告；失败时投递 `SESSION_DELETE_ERROR_V1`。

默认不会删除全局记忆，也不会删除稳定 Worker Scope，因为它们不归单个 Session 独占。插件如果要在删除前把知识留下，应在 `before` 回调中显式 `promote`，不要依赖 fire-and-forget 后台任务。

## 6. 公开事件与权限

可订阅事件包括：

- `MEMORY_RECALLED_V1`、`MEMORY_WRITTEN_V1`、`MEMORY_DELETED_V1`、`MEMORY_PROMOTED_V1`、`MEMORY_OPERATION_ERROR_V1`
- `SESSION_COMPACTION_BEFORE_V1`、`SESSION_COMPACTION_AFTER_V1`、`SESSION_COMPACTION_ERROR_V1`
- `SESSION_DELETE_BEFORE_V1`、`SESSION_DELETE_AFTER_V1`、`SESSION_DELETE_ERROR_V1`

这些事件至少要求 Manifest 声明 `memory.read`；压缩前事件还要求 `memory.write`，因为其设计用途是在历史替换前完成记忆捕获。缺少权限时，插件在贡献预热阶段失败关闭，而不是静默收不到事件。
