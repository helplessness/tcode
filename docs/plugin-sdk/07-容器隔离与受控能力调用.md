# 容器隔离与受控能力调用

本文说明未知 Python 社区插件如何在独立 Docker 容器中运行，以及它如何安全调用网络、命令、BenchThread Tool、MCP Tool 和 Skill。

## 1. 最终运行模型

未知插件不进入 Web/Agent 主进程，也不直接接触 Docker、Sandbox Runner Token、用户工作区、MCP 连接或 Skill 运行环境。

```text
Agent ToolExecutor
    │ 真实用户、租户、Workspace、Policy、Approval 上下文
    ▼
插件 Host Adapter ── Worker v2 双向协议 ── 未知插件 Docker 容器
    ▲                                      network=none / read-only / non-root
    │ capability.invoke
    ▼
Capability Broker
    ├─ process.run ──> plugin_runtime ──> Sandbox Runner ──> tcode-executor
    ├─ network.request -> plugin_network -> Egress Proxy -> Internet
    └─ tools.invoke ──> AgentToolExecutor
                         ├─ Builtin Tool
                         ├─ MCP Tool
                         └─ skill_run ──> Sandbox Runner ──> Skill 专用容器
```

关键点是“代码隔离”和“能力执行”分离：

- 插件代码在自己的无网络容器运行；
- 插件只能发送结构化能力请求，不能发送 Docker 参数；
- Host 用当前真实调用身份重新校验 Manifest 申请、管理员授权、工具副作用、Policy、Approval 和 Sandbox；
- Tool 或 Skill 需要的镜像、网络和挂载由 Host/Runner 决定，不由插件决定；
- 调用结束、超时、卸载或连接断开时，Worker 和活动 Broker 任务都会回收。

## 2. 插件容器里需要安装什么

固定镜像 `tcode-plugin-runtime:py312` 已包含：

- Python 3.12；
- `tcode_agent.plugin_sdk` 公共运行时；
- Worker v2 协议实现。

插件容器不需要也不应该安装：

- Docker CLI 或 Docker Socket；
- `tcode-executor`、Browser、BLAST 等工具镜像内容；
- MCP Server 的依赖或凭据；
- Skill 的运行环境；
- Sandbox Runner Token；
- Host 的完整 BenchThread 源码。

这些能力在插件请求后，由 Host 转发到各自已有的 Tool/Sandbox 环境执行。

### 文献插件统一新版入口（2026-10-20）

文献研究插件现在要求 SDK `>=1.6.0,<2.0.0`，使用 `PluginMetadata`、`start(ctx, config)`、`ToolDefinition/ToolOutput` 和 `stop(reason)`；不再提供 `initialize/get_tools/get_hooks/after_register/shutdown` 入口。

- 保留原23个工具及检索、PDF、文献库、Wiki业务实现，内部业务操作由新版handler调用，不复制第二套实现。工具按需发现；paper Agent的显式工具权限继续生效，不把23个工具默认加入普通聊天目录。
- Agent、Team、Skill和MCP仍由宿主按Manifest发布。按配置生成的运行策略改用 `ctx.prompt.contribute`，宿主通过现有 `PromptRegistry` 事务注册、预算检查和实例token清理；不在Worker里注册宿主Agent，不再做全局source清理。
- 受信Worker可声明 `prompt` 贡献，Host仅接收贡献描述符；实际正文通过有界 `prompt.render` 请求按Agent渲染。未知社区Worker仍不能贡献生产Prompt或订阅宿主事件，没有新增文件、进程、网络或MCP权限。
- 普通宿主启动的会话自举改用公开的session-start/bootstrap观察事件，校验事件工作区；桌面团队自举继续由已有宿主机制负责。观察事件不写回Hook输出对象。
- `ToolCallContext.execution`只传宿主选择的工作区、归属和资源上下文；普通宿主调用额外保留本轮入库确认入口及取消信号。这些回调/事件对象不序列化到Worker，不赋予文件或计算授权。

公共 `plugin_sdk.worker` 只接受新版SDK，不再导入宿主私有插件/工具类型。迁移验证后移除了临时 `plugins/legacy_worker.py`、旧Worker工具分支及对应旧兼容测试，改为测试旧入口明确拒绝。宿主PluginManager中其他旧加载路径尚有独立测试和潜在外部调用方，本次没有顺手删除；也没有重写文献业务依赖。因此本插件仍属于官方受信插件，并非已经完成“全部业务只依赖公共SDK、可作为未知社区插件分发”的迁移；就绪度报告仍如实记录剩余私有业务依赖。

### 迁移后的三处边界修复（2026-10-20）

- **用户入库意图**：SDK调用上下文增加宿主选择的 `user_messages`，最多最近3条完整用户文本，每条最多16 KiB UTF-8。遇到超限文本就停止向更早回溯，不截断句子、不跳过未知轮次去找更早的同意；较新的完整消息仍保留。助手消息不作为用户证据。该快照经现有Worker协议传递，文献业务上下文恢复这些用户消息。标题、任务编号和来源URL不再用于推断同意或拒绝入库；证据不足时沿用原有确认/取消流程。原有显式 `confirmed_by_user`、`force_reindex` 参数语义不变，没有新增授权标记或后台计算通道。
- **迟到提问**：`request_input` 在每次回调前和等待返回后都检查本次调用是否仍有效、是否已取消。旧答案解析等待期间调用若已结束，不再继续发起提问；迟到的答案也不交回业务。没有改动目标问题的持久化、超时默认值或异步恢复状态。
- **结构化输出策略**：Prompt贡献增加默认关闭的 `structured_output_safe`。JSON Schema输出仅合并显式选择支持的贡献，并继续执行Agent范围、宿主预算和失败处理。paper研究策略显式加入；其他贡献即使 `required=True` 也不会因此进入结构化输出。普通文本模式保持原有贡献合并行为，没有按paper名称硬编码研究路线，也没有放开未知Worker的生产Prompt权限。

回归新增覆盖：中英文拒绝、明确保存、标题误导、助手消息、超限历史、显式合法参数；调用结束/取消期间旧答案返回及迟到提问；结构化输出保留paper策略、跳过普通格式提示，普通Agent不受paper策略影响。普通与真实Seatbelt Worker均使用仅含合成数据的PDF路径验证拒绝后不入库，原文件字节不变；测试不解析该拒绝夹具、不提交计算，也不读取或修改用户原始PDF。

插件自身导入的第三方 Python 库需要单独处理：

- 纯 Python 依赖推荐 vendor 到插件包目录，Worker 会把包根加入 `sys.path`；
- 不允许插件启动时在线执行 `pip install`；
- 带原生二进制的依赖必须经过供应链审核后重建固定插件镜像；
- 若某段脚本通过 `ctx.process.run()` 在 `tcode-executor` 中执行，该依赖还必须能在 executor 镜像中使用，或随插件包一同 vendor；
- 插件不能在 Manifest 中指定任意镜像，镜像由 Runner 管理员固定。

## 3. 权限是申请，不是授权

未知插件可申请以下 Broker Scope：

| Scope | 用途 | 工具副作用最低值 |
| --- | --- | --- |
| `process.exec` | 在临时插件副本中运行指定命令 | `process` |
| `network.outbound` | 经 Egress Proxy 请求指定域名 | `read` |
| `tools.invoke` | 调用指定 Host Tool 或 MCP Tool | `process` |
| `skills.invoke` | 限制 `skill_run` 可调用的 Skill 名称 | `process` |
| `sandbox.profile` | 允许进程请求指定 Sandbox Profile | `process` |

Manifest 例子：

```json
{
  "permissions": [
    {
      "scope": "network.outbound",
      "patterns": ["api.example.com:443"],
      "required": false
    },
    {
      "scope": "tools.invoke",
      "patterns": ["paper_search", "mcp_biology_lookup", "skill_run"],
      "required": true
    },
    {
      "scope": "skills.invoke",
      "patterns": ["document.pdf"],
      "required": false
    }
  ]
}
```

管理员必须在插件运行配置中再次授权，而且只能取 Manifest 申请的子集：

```json
{
  "name": "community-report",
  "path": "/srv/tcode/community-plugins/community-report",
  "enabled": true,
  "permissions": {
    "network.outbound": ["api.example.com:443"],
    "tools.invoke": ["paper_search", "skill_run"],
    "skills.invoke": ["document.pdf"]
  }
}
```

未知插件使用默认拒绝语义：Manifest 中 `required: true` 的权限没有管理员显式授权时，插件加载失败；可选权限未授权时不会出现在 Worker 有效授权中。

不要给未知插件配置 `tools.invoke: ["*"]`、`network.outbound: ["*"]` 或宽泛 MCP 通配符。授权应精确到实际 Tool、Skill 和域名。

## 4. 调用 Host Tool 或 MCP Tool

插件先在 Manifest 申请并由管理员授权 `tools.invoke`，然后在工具处理器中调用：

```python
async def generate(arguments, call):
    """调用已授权 Host Tool，并检查其结构化执行结果。"""

    result = await ctx.tools.invoke(
        "paper_search",
        {"query": str(arguments["query"])},
        timeout=120,
    )
    if result.get("error"):
        raise RuntimeError(str(result["error"]))
    return ToolOutput(
        title=str(result.get("title") or "检索结果"),
        content=str(result.get("output") or ""),
        metadata={"delegated": True},
    )
```

MCP Tool 的调用方式相同，`tool_id` 使用 Host Tool Catalog 中的真实 ID。Broker 不直接连接 MCP；它把调用重新送回 `AgentToolExecutor`，因此 MCP 的连接状态、参数 Schema、权限、超时和错误处理仍由 Host 负责。

返回值只包含标题、正文、脱敏错误、截断标志，以及状态/Artifact 类的最小元数据；Host 绝对路径、容器名、环境、命令、内部 Policy 和凭据不会传入未知插件。

调用自身插件贡献的工具会被拒绝，跨层递归还受最大调用数和最大深度限制。

## 5. 调用 Skill

Skill 需要双重授权：

1. `tools.invoke` 必须允许 `skill_run`；
2. `skills.invoke` 必须允许参数中的精确 Skill 名称。

```python
result = await ctx.tools.invoke(
    "skill_run",
    {
        "skill": "document.pdf",
        "action": "run",
        "input_path": "artifact://input/document.docx"
    },
    timeout=600,
)
```

插件容器不会启动 Skill 容器。`skill_run` 重新进入 Host 后，由现有 Skill 路由选择 executor、Browser 或其他专用镜像，并继承当前用户、租户、Workspace、取消信号和审计元数据。

## 6. 运行命令

```python
result = await ctx.process.run(
    "python3",
    ("plugin/scripts/normalize.py", "--format", "json"),
    timeout=60,
)
```

未知插件的进程执行语义：

- Worker 容器不获得子进程能力；
- Host 把插件包复制到当前 Workspace 下的一次性暂存目录；
- `plugin_runtime` 在 `tcode-executor` 中执行命令；
- 工作目录固定为暂存根，插件文件位于 `plugin/`；
- 不挂载完整用户 Workspace；
- 命令结束后暂存目录删除；
- `command` 必须命中 `process.exec` 授权；
- 自选 Profile 还必须命中 `sandbox.profile` 授权。

当前接口不提供持久写回。需要读取或写入用户内容时，应调用经过授权的 Host Tool、MCP Tool 或 Artifact 型 Skill，而不是尝试猜测宿主路径。

## 7. 网络请求

```python
response = await ctx.network.request(
    "GET",
    "https://api.example.com/v1/items",
    headers={"Accept": "application/json"},
    timeout=30,
)
```

网络边界：

- 插件 Worker 始终是 `--network none`；
- Host 先校验 `network.outbound` 的域名或 `域名:端口`；
- 只允许 HTTP/HTTPS 和固定方法集合；
- 显式私网、环回、链路本地等 IP 会被拒绝；
- 生产必须配置受控 Egress Proxy，由代理阻止私网解析和 DNS Rebinding；
- 禁止 Host、Proxy-Authorization 等危险 Header；
- 禁止自动重定向；
- 请求体上限 1 MiB，响应体上限 2 MiB；
- 网络请求在 `plugin_network` 固定 Profile 中运行，不在 Web 主进程发出。

## 8. 生产部署

先在仓库根构建固定镜像：

```bash
docker build -t tcode-plugin-runtime:py312 \
  -f deploy/plugin-runtime/Dockerfile .
```

生产环境至少配置：

```bash
TCODE_PLUGIN_ISOLATION_BACKEND=container
TCODE_PLUGIN_CONTAINER_IMAGE=tcode-plugin-runtime:py312
TCODE_PLUGIN_CONTAINER_USER=65532:65532
TCODE_PLUGIN_CONTAINER_MEMORY=768m
TCODE_PLUGIN_CONTAINER_CPUS=1
TCODE_PLUGIN_CONTAINER_MAX_WORKERS=32
TCODE_PLUGIN_RUNNER_ALLOWED_PLUGIN_ROOTS=/srv/tcode/tcode/plugins,/srv/tcode/community-plugins

TCODE_SANDBOX_REQUIRE_RUNNER=true
TCODE_SANDBOX_RUNNER_URL=http://127.0.0.1:19091
TCODE_SANDBOX_RUNNER_REQUIRE_TOKEN=true
TCODE_SANDBOX_RUNNER_ALLOWED_TOOLS=bash,exec,browser,skill_run,plugin_runtime,plugin_network,plugin:*
TCODE_SANDBOX_EGRESS_PROXY=http://egress-proxy:3128
```

同时从 `config/templates/sandbox_runner_tool_policy.example.json` 安装 Runner 策略。插件目录必须位于允许根下，目录对容器 UID 可读，但不应对无关系统用户可写。

生产部署中只有独立 Sandbox Runner 系统账号能访问 Docker。Web/Agent 账号只持有 Runner Token；插件容器既没有 Token，也没有 Docker Socket。

## 9. 验证与排错

检查镜像和 Runner：

```bash
docker image inspect tcode-plugin-runtime:py312
scripts/start_sandbox_runner.sh status
```

检查插件：

```bash
python scripts/plugin.py validate /path/to/plugin
python scripts/plugin.py test /path/to/plugin
python scripts/plugin.py doctor /path/to/plugin
```

常见失败：

| 现象 | 原因 |
| --- | --- |
| `required plugin permission denied` | 管理员没有显式授权必需 Scope |
| `side_effect_level is too narrow` | 工具声明的副作用低于实际能力 |
| `plugin permission denied` | Tool、Skill、命令、Profile 或域名未命中授权 |
| `active AgentToolExecutor invocation` | 脱离真实 Agent 工具调用尝试调用 Host Tool |
| `worker limit reached` | 同时活动的插件容器达到运维上限 |
| `controlled egress proxy` | 网络能力启用但没有受控出口代理 |
| Runner 400 `tool is not allowed` | `plugin_runtime` 或 `plugin_network` 未加入 Runner 白名单/策略 |

## 10. 已知限制与风险

- 未知插件当前只能贡献 Tool；不能贡献 Prompt、Event、Command、Skill、Agent 或 MCP Server。
- 外部原生 Python 依赖不能由插件在线安装，需要审核并重建固定镜像。
- 一插件一容器会增加启动延迟和内存占用，管理员应设置容器总数上限并监控并发。
- Egress 安全依赖代理正确拒绝私网、元数据服务和 DNS Rebinding；只做 URL 字符串校验不够。
- 委派 Tool/Skill 可能触发用户审批或长任务，插件必须处理超时、取消和结构化错误。
- 权限通配符会显著扩大攻击面，应使用精确名称和域名。
- 进程暂存区是一次性的，不应被当成持久插件数据目录。
- 容器隔离降低未知代码风险，但不能替代包签名、依赖审计、撤销、日志脱敏和运行监控。
