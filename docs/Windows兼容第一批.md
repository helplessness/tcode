# Windows 兼容第一批：文件锁与平台导入

本批不是 Windows 全功能支持，也不提供 Windows 安全沙箱。
不改本地配置、MCP 协议、目标模式预算、审核或异步恢复状态机。

## 已调整的边界

- `tcode_agent/file_lock.py` 为已有调用点提供排他进程锁。
- Linux/macOS 保持 `fcntl.flock`，既有 sidecar 锁保持原路径；短事务的等待策略见下文加固记录，底层锁接口仍保留默认阻塞行为。
- Worker 记忆初始化改为复用继承读写方法的同一把 sidecar 锁，避免新文件尚未写完时另一进程读取；迁移内容和已有文件不变。部署时需重启旧进程，避免新旧初始化实现混跑。
- Windows 使用标准库 `msvcrt.locking`，固定锁定第一个字节，保存并恢复文件偏移，空文件不补写内容。
- Windows 使用非阻塞尝试及等待循环，避免 CRT 默认阻塞锁十次尝试后退出、与 POSIX 无期限等待不一致的问题。
- 非阻塞竞争返回 `BlockingIOError`；显式超时返回 `TimeoutError`；其他错误不作为竞争无限重试。
- 不支持的平台不能退化为无锁；检查点、会话及注册表不再以线程锁或跳过锁冒充跨进程互斥。
- 不改 JSON 原子替换流程；验证替换失败后旧文件保留，临时文件清理。
- 插件 Worker 延迟导入 `resource`：模块可以导入，但缺少资源限制支持时拒绝启动受限 Worker，不运行无约束社区插件。

调用者仍负责线程内互斥、重入、锁文件生命周期和写缓冲刷新。锁文件不能在其他进程可能等待时删除；有意保留的 `.lock` 文件不是卡死依据。

Windows 字节锁与 POSIX advisory flock 并非完全相同：不要把此接口当成允许其他句柄任意读写被锁文件的保证。第一批以本地文件系统为验证范围，不宣称共享网络盘已受支持。

## 第一批后续加固

参考 Codex 的[写入锁协调](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/writer_lock.rs)和 OpenClaw 的[插件锁封装](https://github.com/openclaw/openclaw/blob/main/src/plugin-sdk/file-lock.ts)，借鉴有界等待和明确错误，不移植 PID 过期锁回收或额外锁服务。

- 短状态事务（JSON 存储、检查点、会话事件、Worker 注册表）在后台线程每次获取文件锁最多等待 30 秒。直接位于事件循环时只尝试一次，竞争即返回 `StateLockBusy`，不睡眠等待、不创建脱离请求的后台写入。对应会话和检查点线程锁也采用有界/非阻塞策略。
- `state_lock_busy` 的 HTTP 响应为 409，说明状态操作没有取得锁，不携带内部路径。它不代表远端计算没有提交，也不能据此自动重提计算任务。WebSocket 沿用现有错误处理，本批未新建通知 UI。
- 底层 `lock_file` 的默认语义未全局改变：本体构建、证据维护等显式长任务仍保留原锁策略。不同锁顺序获取时等待上限分别计算，不宣称整个请求最多 30 秒。
- 会话已有的完整线程保存任务被保留；收到取消后等待其写盘完成或失败，再释放外层会话保护并传播取消。重复取消也不会提前释放；如果已开始写盘，取消不承诺撤销写入。这不是后台新增任务，且没有新增远端重试。
- 审计/路由日志用独立 `.lock` 串行化，后台每次锁等待最多 1 秒。POSIX 同时持有原数据锁，兼容旧写入进程；Windows 不锁日志内容，避免普通读者撞到字节锁。Windows 更新必须停止旧版本写入者后整体重启，不能新旧混跑。日志仍保留原有必需/尽力写入策略，没有将诊断日志提升为业务状态。
- 独立区分竞争等待超时与底层文件系统 I/O 超时，后者不误报为状态忙。
